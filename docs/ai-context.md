## Что это

**boks** (https://tryboks.com) — веб-приложение (PWA, mobile-first): свайп-лента **законченных коротких литературных произведений**, каждое читается за ≤15 минут. Одно произведение называется **bok** (мн. ч. **boks**; «a boks» — неправильно).

Три роли:
- **Читатель** — открывает приложение и сразу читает. Лента одна, алгоритмическая, без выбора жанра/настроения/алгоритма. Свайп вправо-влево = следующий/предыдущий bok.
- **Автор** — публикует свои тексты через кабинет (`/author`), после модерации.
- **Админ (основатель)** — модерирует, импортирует каталог и **сравнивает алгоритмы рекомендаций по измеренному поведению читателей** (A/B-эксперименты в `/admin`).

Главная исследовательская цель: проект — основа магистерской работы (ВКРС) по сравнению рекомендательных алгоритмов по поведенческим метрикам. Документы по ней — `docs/thesis/` (на русском).

Боль, которую решаем: у человека 15 свободных минут, а выбор «что почитать» дороже самого чтения. Продукт снимает выбор целиком.

## Разделы для читателя

- **feed** (`/`) — основной продукт: одна ранжированная под читателя лента.
- **series** (`/series`) — полка «boks series»: произведения в особых форматах (озвучены живым голосом, с иллюстрациями; стих появляется внутри картинки). Сейчас 20 штук (10 EN, 10 RU; 19 стихов + «Лев и собачка» Толстого с интерактивными моментами). Каждое из них **также есть в ленте** с пометкой «listen to the production».
- Форматы: **cinema** (проза: озвучка + сцены + «story moments», где история просит жест) и **immersive poem** (стих).
- `/b/<id>` — ссылка на конкретный bok (server-rendered для превью в мессенджерах), `/a/<handle>` — страница автора.

Каталог: ~900 произведений общественного достояния (английские и русские классики: Чехов, Блок, Дикинсон, Тисдейл и т.д.), импортированы под одним аккаунтом-издателем `@boks`, у каждого свой byline. Около половины — стихи, медиана длины ~1 минута. Интерфейс только на английском; тексты на своём языке. Читатель выбирает языки чтения (жёсткий фильтр).

## Ключевые продуктовые правила (не нарушать)

- Нет кнопки «прочитал»: **read / skip** выводятся из foreground-времени на экране и прогресса скролла. Время на заблокированном телефоне не считается.
- **Гости** (анонимная сессия Supabase) читают без регистрации; мягкие напоминания после 5 и 10 boks, обязательная регистрация после 15. Гости могут читать комментарии; лайк/коммент/подписка — только с аккаунтом.
- Вход **только без пароля**: email OTP (magic link или 6-значный код). Никаких полей пароля.
- Человек идентифицируется только уникальным `@handle` (латиница, цифры, `_`, 3–24 символа, начинается с буквы). Display name нет. **Byline** — псевдоним, выбираемый при публикации конкретного bok, не меняется вслед за handle.
- Автор: ≤15 минут чтения, не более 3 заявок в сутки (UTC, проверяется в БД), публикация только после одобрения админа и подтверждения прав.
- На экране чтения нет метаданных (жанр, время чтения) — интерфейс минимальный, контролы появляются по тапу.
- Метрики админки — только измерения из `recommendation_events`, никаких выдуманных составных скоров. `likes` и `comments` — продуктовые фичи, не метрики поведения.

## Стек и архитектура

- **Frontend + сервер**: Next.js App Router на **vinext** (Next на Vite), React 19, TypeScript, Tailwind 4, shadcn/ui (Base UI/Radix), lucide. Деплой — один **Cloudflare Worker** `read` (wrangler).
  - Важно: `next/link` в этой сборке не работает для навигации между разделами — используются обычные `<a>`.
- **Данные и auth**: **Supabase** (Postgres + RLS + RPC-функции, анонимные сессии, email OTP). Единственное хранилище. В браузере только publishable key; service-role ключ нигде в коде/фронте.
- **Ранжирование**: чистый TypeScript в `lib/boks/recommendations/`. Выполняется в Worker на `POST /api/feed` (Worker пробрасывает JWT читателя, сам не имеет повышенных прав). БД отдаёт кандидатов со счётчиками, TS их упорядочивает. Браузер ранжирует тем же кодом только как помеченный fallback (circuit breaker).
- **Эмбеддинги**: `multilingual-e5-small` для семантического сигнала.
- Тесты: Vitest (юнит), проверки схемы/RLS на одноразовом Postgres в Docker, полный флоу на локальном Supabase.

### Поток ленты
1. Браузер получает visitor id + анонимную/реальную сессию Supabase.
2. `POST /api/feed`: Worker грузит конфиг эксперимента и кандидатов (`get_recommendation_candidates` — опубликованные boks на языках читателя, ~400 штук, половина новейших + половина случайных), определяет **arm** читателя (детерминированно, хранится в `recommendation_assignments`), ранжирует `buildReaderFeed`, сохраняет `served_feed` (для воспроизводимости) и отдаёт **slate**.
3. Все действия читателя → `reader-events.ts` (батчи, ретраи, keepalive) → RPC `record_recommendation_events` с атрибуцией: алгоритм, эксперимент, позиция, feed id, foreground-секунды, прогресс. Типы событий: impression, start, complete, skip, like, share, comment, heartbeat, aftertaste.

### Рекомендации и эксперименты
- Алгоритмы (стратегии) в `lib/boks/recommendations/strategies/`: `for_you` (control, сейчас единственный живой arm), `completion_first` (припаркованный challenger), `balanced`, `discovery`, `taste_match`, `reaction_first`, `recency`, `random_control`. Добавить алгоритм = один файл + строка в `index.ts` + тест в `feed.test.ts`.
- Сигналы нормированы в 0..1 (`deriveFeedSignals`): усталость, новизна, аффинити к автору (по byline), семантика и т.п. Веса задаются вручную, ничего не обучено.
- Сравнение на уровне читателя (один читатель = одна выборка), интервалы, p-value, мощность считаются в `lib/recsys/aggregate/metrics.ts`. Если интервал пересекает ноль — «inconclusive».
- Честные ограничения: ~50 активных читателей → эффекты слабо детектируются; interleaving спроектирован, но не реализован; нет MostPop-бейзлайна; нет явного негативного фидбэка; жанр/настроение у всех boks одинаковые (дефолты), их надо выводить из текста.

## Жёсткие ограничения при изменениях

- Никаких секретов (service-role, API-ключи) в коде, фронте, wrangler vars, доках.
- Никогда не грузить весь каталог в сессию — только ограниченные батчи и серверная пагинация.
- Не править применённые миграции; новая таблица/вьюха для Data API получает grants в той же миграции; предпочитать `security definer` RPC с проверками.
- Не откатывать Worker отдельно от схемы — прод-схема ушла вперёд, деплоить из текущих исходников.
- Права админа — только `user_profiles.role` через RLS/RPC, никогда localStorage/URL/user_metadata.
- В Tailwind не склеивать класс с интерполяцией (`` `foo${x}` ``) — класс не сгенерируется.
- Цвета — только через CSS-токены из `app/globals.css` (светлая и тёмная тема).

npm run lint && npm run typecheck && npm test   # офлайн

## Текущее состояние и открытые задачи (кратко)

- Прод работает: лента с Worker-ранжированием (`ranking.v2`), гости, аккаунты, комментарии с ответами, подписки, кабинет автора, админка с воронкой гостей, странами (CF-IPCountry, IP не хранится) и лабораторией экспериментов. Последний большой аудит и деплой — 2026-10-05.
- Наблюдения с прода: гости уходят рано (медиана ~24 с чтения), до стены регистрации почти никто не доходит.
- Очередь: (1) выводить жанр/настроение из текста; (2) больше русской прозы; (3) перевести оставшиеся ~20 мест показа ошибок на `readableBoksError`; (4) ротация ключа Resend; (5) доказать доставку писем третьим лицам; (6) MostPop-бейзлайн и interleaving для диссертации.
- Известное: холодный Worker может держать «Loading» ~8 с; метка read/skip считает слова по английской норме (смещение для русского и стихов); у читателей из РФ возможна блокировка домена `*.supabase.co` (вариант — проксировать через свой домен).
